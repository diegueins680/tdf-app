Recommended shared admission boundary

Keep existing lock order. Direct: Event -> Tier pricing. Legacy Stripe: Event -> optional terms policy -> Tier pricing -> Promo. Canonical: idempotency advisory lock -> Event -> expire old holds -> Tier -> policy -> Promo. Once every relevant row is held, read one database wall-time sample in a separate SELECT clock_timestamp() statement. Use that SAME admission time for the locked current tier's sale window and the locked selected promo's date window, before new inventory/redemption/order effects. Retain inclusive start/end behavior: start <= admission <= end. Do not import payment-intent's exclusive end rule. Missing promo imposes no promo-date condition.

The least disruptive implementation can share the database-clock reader and a precise caller contract while retaining Inventory's current signature: all three callers obtain fresh admissionTime after their final locks, validate the already locked promo against it, and pass it into reserveTicketInventory. Reacquiring already-owned Event/Tier locks inside Inventory cannot introduce another row-lock wait. Keep promo financial policy in the caller; Inventory remains inventory authority. Rename or document the timestamp as admission time to distinguish it from audit time. This relies on participating callers and requires call-site tests; it does not make arbitrary stale timestamps unrepresentable in the helper API. A stronger lock-token/callback API is optional complexity, not necessary to repair these three callers.

Do not instead sample internally in Inventory while validating promo with a different earlier sample, or capture time after Event but before blocked Tier/Promo/policy reads. Do not use transaction-start now()/CURRENT_TIMESTAMP, statement-start time, or a clock_timestamp expression evaluated before a locking SELECT finishes. The date-validation sample is a declared admission linearization point while relevant rows are held, not a claim that transaction commit/provider execution occurs before expiry. Database clock synchronization/nonmonotonic correction assumptions should be explicit.

Preserve handler now separately for established audit/order timestamps, immutable snapshots, purchased history and existing duration policy. Inventory's updatedAt currently uses its time argument, so passing admissionTime changes that stock-audit timestamp to actual admission; distinguish this deliberate effect from rewriting order purchase timestamps. No new provider POST/readback is needed for creation-time tests.

Canonical transaction and replay cautions

There are two canonical reuse branches: outer lookupTicketCheckoutIdempotency around :515, and the advisory-serialized existing-runtime branch around :596. Place fresh validity checks only in createNew, preserving both exits and their request-hash checks. Existing canonical outer flow already validates current tier/promo before the first lookup. Therefore preserving its current reuse branches does not establish a new promise that any historical replay survives arbitrary current expiry; changing that outer ordering is a separate behavior change. Legacy Stripe's existing-checkout branch must likewise bypass the new reservation check.

Canonical expire_holds intentionally runs before Tier/Promo locks because its checkout/runtime/tier trigger locks must remain compatible with status polling. Do not move it after those locks to share the final sample. It may use a separate earlier cleanup sample, or retain its existing timestamp if this is scoped; final NEW-reservation authority must still be freshly sampled afterward. Cleanup may legitimately expire other holds even when the new buyer is refused, so the regression's no-effects assertion should target the refused buyer's new reservation/order/redemption, not falsely require every system row unchanged.

Canonical holdExpiresAt is computed before the transaction from the existing audit now plus policy duration. A long wait can shorten or exhaust that duration. The user's new sale/promo-validity rule alone does not authorize silently resetting or extending stored hold deadlines, changing approval-policy windows, or reworking terms acceptance. Preserve this existing duration contract and record the distinct stale-hold issue unless explicitly included with authoritative acceptance criteria. Policy effective_until uses an exclusive boundary, unlike promo/tier; do not merge these interval semantics casually.

Backend and rollback assumptions

Inventory already contains PostgreSQL-specific FOR UPDATE and ::bigint syntax; its three reservation paths are not a demonstrated SQLite concurrency abstraction. A shared PostgreSQL clock query adds no claim of portable concurrent reservation. Preserve existing early-refusal SQLite compatibility by avoiding newly unconditional SQL clock calls before the admission path; test any fallback if one is added. No reversed lock order, independent transaction or unlocked second promo read is needed.

Validate promo time before inventory mutation. Both direct and canonical transaction wrappers can return Either without rolling back ordinary SQL writes; a late Left after reserving stock would commit an unintended reservation unless explicitly compensated or thrown/rolled back. Pre-effect validation avoids this regression. Existing atomic promo-cap claim/compensation remains authoritative and unchanged.

Verification recommendations and limits

Actual-handler lock-wait tests should cover direct tier expiry, legacy Stripe tier and promo expiry, and canonical tier and promo expiry. A fully discounted legacy checkout avoids provider transport; canonical creation may retain a positive total and test only creation, which does not require a provider call. Witness the actual wait and database time strictly past the deadline before releasing. Include a wait on the LAST Tier/Promo fence, not only Event, live-window acceptance, inclusive-boundary pure checks, and prior-order/idempotent compatibility. Bound waits and release/join workers on all exits. Stale request time, transaction-start time and pre-last-lock time are meaningful negative controls. No runtime outcomes are claimed here. Existing snapshot models explicitly excluded elapsed clock and cannot be promoted to this new requirement without new evidence.
