Primary-source basis

CSSOM View13.1 specifies that resize steps compare dimensions changed since their previous execution and then fire Window/VisualViewport resize events. This supplies notification ordering, not a promise that reading clientWidth means delivery already occurred. The cited snapshot is a W3C Working Draft and must be identified as such.
https://www.w3.org/TR/2025/WD-cssom-view-1-20250916/#resizing-viewports

HTML's current update-the-rendering algorithm queues rendering work and invokes resize steps in that work before later rendering stages. It does not turn an external viewport-setting protocol return into an acknowledgment that JavaScript listeners already ran. The event-loop algorithm supports observing the input notification before demanding an event-driven JavaScript result.
https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering

Installed Popper attaches window.resize to instance.update; debounce schedules the update through Promise resolution and forceUpdate recomputes geometry. A next task after that delivered event is a concrete boundary for those callbacks/microtasks. It is not a universal browser convergence/paint-time theorem or an all-widget completion contract.

Required acceptance and lifecycle safeguards

1. Keep the first atomic root overflow and visual-scale results immutable, attach them and assert them strictly before any native-resize acknowledgment can provide acceptance. Original standards/client-bound preconditions and zero root-overflow tolerance remain intact. An initial root/zoom failure must still fail even if all later samples fit.
2. Register the acknowledgment before requesting viewport320. Bind it to actual Window resize for that requested width, preferably requiring event.isTrusted. An unrelated prior event, synthetic dispatch, layout rectangle, Popper mutation or a fit predicate is not acknowledgment. A delivered requested resize followed by one task is the revised overlay phase; do not poll helper/root dimensions until they pass.
3. Fail closed when the native acknowledgment is absent after the fixture's8-second bound. This is a finite test-scheduling deadline, not a new product latency SLA. Clear timeout/remove listener on success, timeout and early initial-assertion failure. Avoid an unobserved rejecting Promise if the earlier root check aborts the case. Retain observation snapshots/cleanup without leaking them into application behavior.
4. At the first post-acknowledgment observation, require the expected still-focused helper, unchanged content/name, same edge tolerance, root/scale fit and existing nonvacuous scroll tracking. No test forceUpdate, extra product listener, dismissal, clipping, arbitrary delay or retry-to-green is warranted by these traces.
5. Preserve all a909/21628 literal-contract failures and previous uninstrumented counterexamples. Validate the revised harness on source-identical UI, then require the sole-option-removal control to fail its original immediate root predicate and the helper-only fault to fail the revised strict helper predicate. Deliberately missing/synthetic acknowledgment should not pass. New local/hosted source-bound execution remains necessary; no candidate execution is qualified by this review.

This is a documented specification/harness correction because it replaces an unsupported pre-input-notification demand with a causal input-delivered boundary for a JavaScript overlay. It retains the independent immediate CSS/root safety requirement and a falsifiable helper requirement. It would become mere weakening if it accepted a fit without the event, erased old failures, moved the original root guard, removed strict edges/focus checks or treated later convergence as a substitute for the first root result.
