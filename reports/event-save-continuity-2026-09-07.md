## Outcome

Saved events now converge through the existing Party-owned `directory_favorite` capability instead of remaining device-only. The protected favorite API supports a validated `targetKind` filter, accepts event saves only for positive IDs in the public event projection, and omits previously saved events that are no longer public from event-filtered reads. PUT and DELETE retain idempotent desired-state behavior.

Mobile keeps a Party-scoped cache and a Party-scoped last-desired-state outbox. Reads reconcile against `GET /directory/favorites?targetKind=event`; online writes wait for server acknowledgment, while retryable network/server failures leave a durable local operation for replay. Operations for one Party are serialized, rapid toggles reconcile first, and successful replay retries the onboarding completion handshake. Non-retryable API failures do not remain in the outbox or produce completion analytics.

The unscoped legacy key remains unread during normal saved-event access. The profile saved tab exposes only a count and a confirmation explaining that ownership is unknown. Values are bound to the current Party only after that explicit action; transfer to the Party-scoped cache/outbox completes before the legacy key is removed.

`event_saved` onboarding completion now requires a Party-owned favorite created between authoritative signup and the completion request and joined to the current public event projection. Missing, cross-Party, pre-signup, future, and non-public evidence fail closed; valid evidence completes once.

## Scope and residual risk

No production data, migration, merge, deployment, experiment activation, or customer communication is part of this change. The existing table already has the required Party/kind/target primary key, so no schema migration is needed.

Tests use in-memory SQLite and mocked AsyncStorage/API calls. A real two-device session, app upgrade, iOS/Android storage interruption, accessibility pass, staging authentication, and production PostgreSQL query-plan/runtime check remain unperformed. Saved-event detail hydration still uses existing per-event requests after the synchronized ID read; batching that payload is a separate performance improvement.

The onboarding experiment remains paused because `moment_reaction` evidence and assignment/exposure semantics are still not fully server-authoritative.
