# Durable public ticket confirmations

Public checkout now queues its confirmation inside `finalizePaidTicketOrder`, in the same PostgreSQL transaction that records canonical issuance. The PayPal webhook and browser callback reuse this function. No network send happens inside that transaction and there is no historical backfill on migration. Existing SMTP transport, HTML templates, configuration and delivery suppression are reused; no second ticket, order or payment system is created.

`event_ticket_confirmation_delivery` contains an order reference and operational state only, not recipient PII, ticket codes or rendered message bodies. The primary key deduplicates issuance/webhook retries. One worker claims one due row with `FOR UPDATE SKIP LOCKED`, a random lease and a two-minute expiry. SMTP is bounded to thirty seconds. Completion requires the current unexpired lease; failures back off exponentially, stop after eight attempts and retain a dead-letter record. A crashed lease is recoverable; a partial processing-lease index bounds recovery scans to in-flight jobs rather than retained history. Rollback refuses to discard any queue history.

The worker rereads canonical payment/order state and current ticket ownership. Cancelled, refunded, used and transferred credentials are excluded. When no usable buyer-held ticket remains, delivery is cancelled rather than sending revoked credentials. Receipts carry usable admission codes, the event's timezone (validated against PostgreSQL names, with an explicitly labelled UTC fallback for invalid metadata), the original charged amount, the public event URL and an optional `/app` link. App installation and account creation are not required to use those codes. Transfer invitation delivery and refund/reminder emails are separate work; this change does not claim to implement them.

`accepted` means SMTP accepted the message, not inbox delivery. SMTP and PostgreSQL cannot commit atomically: a process crash after SMTP acceptance and before database acknowledgement may cause a duplicate email on retry. It cannot create a second charge or ticket. Do not describe this channel as exactly once. Logs retain fixed error codes, not exception payloads, recipient addresses or ticket credentials.

Apply `2026-10-05_ticket_confirmation_delivery.sql` and `2026-10-05_ticket_confirmation_lease_index.sql` before deploying its callers. The worker remains off unless `TICKET_CONFIRMATION_EMAIL_ENABLED=true` and SMTP configuration is present. Pending records survive while disabled. Set `HQ_APP_URL` to the canonical HTTPS web origin (`https://www.tdfrecords.net` in production). Enable the worker only after verifying the configured SMTP sender and receipt delivery in the official test environment; migration/code deployment does not activate event sales.

Monitoring (restricted database/operator access): group queue counts by `state`; alert on due pending rows, expired processing leases and any `dead_letter`. Inspect `attempts`, `next_attempt_at` and `last_error_code` without exporting buyer data. A repair should retry retained intent after fixing the sender, not create another order or resend all historical purchases.

Validation:

- The existing public-checkout SQL rehearsal checks paid/issued authority, transactional rollback, deduplication, backoff, foreign/expired lease rejection, crash recovery, retry exhaustion, cancellation, replay and guarded rollback.
- `scripts/test-ticket-confirmation.sh` exercises the actual Haskell worker against a dedicated PostgreSQL database, including eight concurrent consumers, transient failure and current-holder privacy.
- `scripts/test-ticket-confirmation-smtp.py` runs a loopback SMTP server that refuses the first attempt, then captures one actual MIME message after the worker retries. It checks admission codes, public links, optional app usage and message headers. No email is sent to an external recipient. This is not official payment or external inbox-delivery evidence.

Design references: [AWS transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) explains the database/message dual-write failure and duplicate-delivery limitation. [PostgreSQL SELECT locking](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE) documents `SKIP LOCKED` for queue consumers. These principles inform this implementation; no AWS service dependency is introduced.

## Consolidated audit correction

`NOTIF-TICKET-001` owns this boundary. The additive `2026-10-05_ticket_confirmation_lease_clock.sql` locks the delivery row **before** reading `clock_timestamp()` for completion. Transaction-start time cannot authorize a lease that expired during a lock wait. The historical migration is retained unchanged. The correction is forward-only; reverting the function to a stale-clock version is not a supported recovery. Apply it after both preceding delivery migrations.

The direct shell, Haskell and SQL-regression entrypoints reject nonlocal/non-CI routing and inherited libpq host/service overrides before opening a connection. Only their dedicated synthetic database is admitted. The lock-wait regression observes PostgreSQL's blocked finisher, waits for actual expiry, and demonstrates that the old function wrongly accepts while the corrected function rejects; the old function is exercised only inside that disposable fixture.

`formal/event-operations/NotificationLease.tla` abstracts a single intent, two lease identities, one claim, one finishing request and four clock values (0–3), with a two-tick claim lease. It checks fresh-claim, current-lease and unexpired completion safety. Mutations use transaction-start time for claim or completion, or remove lease identity, and must each produce a counterexample. Row locking and atomic database updates are assumptions, tied to separate PostgreSQL tests; SMTP, retry exhaustion, queue scheduling, transfer/refund races, provider delivery and crash recovery are excluded from this small model. Stuttering is allowed, no fairness or liveness theorem is asserted, and bounded checking is not a proof of the worker implementation.

Eligibility is sampled before external SMTP work. A concurrent ownership change can make an already-rendered receipt stale; transfer acceptance rotates credentials, and admission must continue to reject revoked or used credentials. The system cannot retract an email already submitted to SMTP. This audit does not promise synchronous deletion from a recipient's mailbox or exactly-once delivery.

The subsequent additive `2026-10-05_ticket_confirmation_claim_clock.sql` repairs claim creation too: expired rows are selected with `SKIP LOCKED` (up to100 per iteration), and a due row is locked before sampling real time for its two-minute lease. The transaction-start timestamp cannot shorten a newly returned lease. Locked expired rows remain for a later iteration rather than stalling unrelated polling. A server-side post-delay clock anchor regression rejects the historical behavior without depending on client timing; a held expired-row control detects the old blocking recovery and verifies the new skip. Claims and completion still assume transactions commit promptly; process pauses and crashes retain the documented SMTP duplicate possibility.
