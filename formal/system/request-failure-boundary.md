# Request and diagnostic failure boundary

`PRIV-ERROR-001` governs unexpected synchronous errors at the outer WAI request boundary, Warp diagnostics, best-effort authentication activity persistence and Radio provider fetches. A failed request may contain SQL parameters, tokens, private URLs or an exception whose rendering itself throws. None of these exception values may be rendered into responses, stderr or the administrative LogBuffer by these boundaries.

Before response delivery starts, the request middleware reports a fixed error identifier and returns one fixed500 body. The normal configured CORS middleware surrounds this response, so only admitted origins receive their configured headers. Once response delivery starts—including a callback that throws—the exception must propagate to Warp rather than starting a second response. Warp's request-independent exception response has no CORS grant and its logger uses the same fixed identifier. The wrapper marks response delivery atomically before calling the underlying callback; this is not a claim that all HTTP streaming or socket behavior is verified.

Cancellation classified as asynchronous by `safe-exceptions` propagates; it is never converted into a normal500, an activity-persistence failure, or a provider-fetch failure followed by further mutation. Synchronous diagnostic-output failure does not replace a handled response. A diagnostic logger that itself blocks remains outside this boundary's timing guarantees.

Authentication activity remains best effort where it already was. This does not weaken the separate mandatory account-creation consent transaction or make failed audit persistence successful. The fixed warning reports that activity persistence failed. Successful activity writes retain their established private audit metadata; the diagnostic LogBuffer does not duplicate actor identifiers or raw SQL errors. Radio's unused exception strings were not a demonstrated public leak: import discards those details and refresh/now-playing already use fixed outward errors. The repair makes those internal failures fixed and preserves cancellation before follow-on work.

`TDF.App.FailureBoundary` is used directly by Boot, authentication and Radio handlers. `TDF.FailureBoundarySpec` exercises actual middleware/callbacks, synthetic secrets, an exception that cannot safely be rendered, cancellation, response-start behavior, logging failure and trusted/untrusted origins. `scripts/verify-request-failures.py` executes the same tests against the intended source and three isolated source mutations: catch cancellation, respond twice and render arbitrary exception text. A compile error or incomplete Hspec run cannot count as detection. This is finite executable conformance evidence, not a model-checking result, full HTTP-server refinement proof or deployed verification. Other logging/provider boundaries remain separate audit obligations.
