# Event and venue search sync

`/buscar` reads `directory_public_search_document`. Until 2026-10-09, event and venue documents were written only by the one-off August backfill (`directory_refresh_legacy_event_search`), so events created later never appeared.

Migration `2026-10-09_directory_event_search_sync` makes the documents follow their sources:

- **Triggers.** Inserting, updating or deleting a `social_event`, updating or deleting a `venue`, and changing an `external_event_ref` (provider suppression) upsert the affected event and venue documents. Deleting the source removes its document. An event that becomes private or suppressed keeps its cached document, and the public search view filters it out at read time, as required by the event privacy composition contract.
- **Same projection.** The documents come from the privacy-reviewed `directory_public_event` and `directory_public_venue` views. The manual full refresh reuses the same functions, so a rebuild can never disagree with the incremental path. Search still re-checks those views when reading, so a stale row cannot expose a private event.
- **Upcoming events.** For events, `effective_at` holds the start time, which date filters use. The public search view previously hid documents whose `effective_at` was in the future, so upcoming events were invisible. Events are now exempt from that check, and their visibility stays governed by `directory_public_event`.
- **City.** A venue whose city is only free text gets the `city_reference` id when exactly one city matches by normalized name. This applies on insert and update, plus a one-time backfill, so city filters such as "Quito" match. When a venue's city text changes and its id agreed with the previous text, the id follows the new text (the venue API writes only the text), so the venue and its events move to the new city's results. An id that was chosen independently of the text is kept. Only active cities are considered, so a retired namesake is never assigned and does not make the active city ambiguous; a venue whose inferred city is retired later still follows the next edit of its city text.
- **Venues of late-published events.** Every event insert or update also syncs its venue, because publishing an event (a workflow-state change) is what makes its venue listable.
- **Stable versions.** The document's alert-watched columns (`source_version`, status, visibility) are written only when a projected field changes. A rebuild, a re-applied migration, or an edit to something search does not show (capacity, price) leaves them untouched, so saved-search alerts are not evaluated or sent again; the newer `source_updated_at` is recorded by a separate statement that the alert trigger does not watch.
- **Backfill.** The migration indexes events and venues that already exist with saved-search alerts switched off for its own transaction: they are not new results, so deploying does not notify subscribers. Alerts for events published afterwards work as before.
- **Hidden and republished.** A hidden event (private, suppressed, not listable) or a venue with no public event keeps its cached document, marked `paused`. Publishing it again restores `published`, which advances the version, so saved searches created in the meantime are notified.
- **Concurrent edits.** The sync triggers are deferred constraint triggers: they run at commit and take one transaction-scoped advisory lock before reading their sources. A venue edit and an edit or deletion of one of its events therefore cannot overwrite each other's projection with an older snapshot or reinsert a deleted document. Because the lock is only taken at commit, after the transaction holds every source row lock it will take, a transaction that touches several events cannot deadlock on it with a single-event writer. Within a transaction the documents change at commit, not after each statement (`SET CONSTRAINTS ALL IMMEDIATE` restores per-statement sync, as the tests do).
- **Kind words.** Event documents include "evento eventos" and venue documents include "venue venues local locales". A search for "Eventos" therefore returns events.
- **Images.** The result image follows the same rule as the public event detail (`directory_public_rsvp_event`): an HTTPS `imageUrl` whose host carries no credentials, or a same-origin path. A flyer the detail page shows is never a placeholder on the card.
- **Genres and lineup.** An event carries no genre of its own; the genres of the artists on its bill do. Canonical memberships (`event_artist` → `artist_genre_membership.genre_id`, written by the current artist API) are projected directly, and the legacy free-text array (`social_artist_profile.genres`) is mapped to catalog genre ids by code, slug, name or search alias; the union becomes `genre_ids`, so the genre filter and the taxonomy ranking apply to events. Artist names, catalog genre names and unmapped genre words become search text. Changes to the bill, to an artist's memberships, or to an artist's legacy genres or name, resync the artist's events (deferred triggers on `event_artist`, `artist_genre_membership` and `social_artist_profile`).
- **Nearby mode and history.** Consented coordinates live only in memory. The nearby URL (`radiusKm`, no `cityId`) is written with a replace, and choosing a city afterwards also replaces, so no history entry depends on coordinates the page cannot restore; a nearby URL opened cold falls back to the visitor's city.
- **Expiry.** `expires_at` is the end time, or one day after the start when no end time is set, so an open-ended event does not stay listed forever. Past events stay hidden (the pre-existing behaviour).
- **Entity-aware filters.** `/directory/search` applies the profession, service, instrument, availability and remote filters only to profiles and classifieds; events and venues neither carry nor are excluded by them. The genre, city, text, radius and date filters apply to every kind. The web page hides the people-only controls on the Eventos and Venues tabs.
- **Counts.** `facets.total` and `facets.cities` describe the current query (entity type included). `facets.entityTypes` counts every kind under the same filters without the entity type, each as its own tab lists it, plus `all` for the mixed tab (derived artist listings fold into their profile there), so tab counts do not vanish once a tab is selected.
- **URL state.** On the web, the search URL is the single source of state: a deep link such as `/buscar?entityType=event&cityId=…` hydrates the tab, the city and the results; user actions push history entries, so back and forward restore the previous search; a missing city is completed with the visitor's last city by a replace.
- **Reindex.** `SELECT * FROM directory_event_search_reindex();` runs the full refresh and reports `events_examined`, `events_eligible`, `events_skipped_not_public`, `venues_eligible`, `documents_inserted/updated/unchanged/paused/deleted` and `events_unresolved_city` (public events whose venue city could not be resolved to a selectable city, for manual review). It is idempotent: unchanged sources keep their version. The migration itself calls it, so the deploy log carries the backfill counts. Outside a migration, disable `directory_search_alert_trigger` first when the indexed events must not notify saved searches.

The rollback removes the triggers and helpers and restores the previous view and refresh. Derived documents and resolved city ids are kept.

Verification: `tdf-hq/test/integration/directory_event_search_sync.sql`, which runs from `scripts/test-music-directory-migration.sh` (apply twice, verify, roll back, reapply, verify).
