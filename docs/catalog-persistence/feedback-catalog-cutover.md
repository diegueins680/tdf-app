# Feedback category and severity cutover

Status: candidate implementation and disposable PostgreSQL 17 rehearsal complete; production has
not been modified.

## Classification and model decision

Feedback category and severity are dynamic business catalogs. They are selectable, localized,
ordered, governable values used by a public form, backend validation, notification email, reports,
and administration. The former web arrays and backend string allowlists were therefore not
technical protocol constants.

The candidate adds two specialized tables:

- `feedback_category`, governed by catalog `feedback-categories`;
- `feedback_severity`, governed by catalog `feedback-severities`.

Each row owns a stable UUID and code, Spanish and English presentation, optional descriptions and
slug, manual order, active/publication lifecycle, creator/editor/approver metadata, effective
dates, deprecation and replacement metadata, usage count, publication revision, and optimistic
version. `feedback.category_id` and `feedback.severity_id` are the canonical relationships.
Retained `category` and `severity` text columns exist only as migration/rollback evidence and the
database rejects any new non-null value.

The defaults are active `catalog_scoped_default` relationships in scopes
`feedback-category/global` and `feedback-severity/global`. A unique index prevents competing
defaults. Publication can atomically replace a default through the typed `globalDefault` draft
field and emits normal catalog audit/revision evidence. A current default cannot be deactivated or
hard-deleted.

## Contract and consumers

- Public `POST /feedback` is explicitly unauthenticated in OpenAPI and accepts required UUID
  multipart fields `categoryId` and `severityId`. Legacy `category` and `severity` fields are
  unknown fields and fail strict decoding.
- The backend validates that each UUID belongs to the correct active, non-deprecated, published
  catalog before insertion. Notification email resolves its Spanish labels from the referenced
  rows rather than trusting caller text.
- The public web page loads both catalogs in one bounded batch, filters to selectable published
  values, uses the persisted defaults, presents labels in the active locale, and blocks submission
  when policy cannot be validated. It has no emergency option array.
- There is no feedback submission feature in the current mobile application. Its generated client
  still receives the canonical multipart schema so a future feature cannot introduce a different
  write contract. Its authenticated Catalogs surface does provide strict category and severity
  draft/review editors with canonical UUIDs and explicit global-default decisions.
- The common protected catalog endpoints expose items, revisions, review/publication, activation,
  ordering, merge/replacement, usage, and CSV operations. Backend authorization remains the
  authority.
- The web Catalogs index is populated from protected persisted definitions. Its contextual
  feedback editor supports both specialized tables, bilingual create/edit drafts, remote search,
  revision submission, approval/rejection, manual order fields, and default reassignment.

The canonical OpenAPI source regenerated byte-identical web and mobile contracts with SHA-256
`9b067867b60ae1450bf9ff13ef243a5c91452a44d9e3677d0f72e0aa87bb40fd`.

## Migration artifacts and safety

- `tdf-hq/sql/2026-08-11_feedback_catalog_cutover_dry_run.sql` is read-only and reports schema
  readiness, every source row, candidate counts, selected UUIDs, evidence, persisted options, and
  defaults.
- `tdf-hq/sql/2026-08-11_feedback_catalog_cutover_apply.sql` takes a transaction-scoped advisory
  lock, enforces a configurable row threshold, records immutable per-row source evidence and
  per-field mappings, validates both foreign keys, clears copied strings, installs strict writer
  triggers, and aborts unless every row is canonical.
- `tdf-hq/sql/2026-08-11_feedback_catalog_cutover_rollback.sql` restores text and previous UUIDs
  only when the current canonical UUID pair still matches the recorded targets. It retains columns,
  catalogs, mappings, run history, and evidence.

Resolution is deliberately narrow: an existing UUID or normalized code/Spanish name/English name
must identify exactly one active published row in the correct catalog. Null, unknown, ambiguous,
or conflicting identities abort the whole transaction. A default is never guessed for an existing
row.

## Production inventory boundary

The sanitized read-only production inventory observed one `feedback` row whose category was
`idea`. That inventory did not capture a severity value, so it is not evidence that the row has a
safe severity mapping. Production apply must remain blocked until the expand schema is deployed,
the current database is backed up, and the new dry-run proves one unique category and severity for
every row. A null or unknown severity will be withheld and will stop the cutover rather than being
silently changed to the current `p2` default.

## Disposable PostgreSQL evidence

The rehearsal used one synthetic legacy row (`Idea`, `P2`) after a candidate schema/bootstrap
start. The read-only report returned one mapped row, one candidate in each domain, and zero
unresolved, ambiguous, or conflicting rows.

Final apply identifiers and counts:

- run code: `feedback-catalog-final-20260811`;
- candidate revision: `local-candidate-v1`;
- run ID: `b7a8f35a-32d5-433d-afdb-3de497fd872a`;
- scanned/mapped/rejected/ambiguous: `1/1/0/0`;
- source evidence rows: 1;
- per-field mapping rows: 2;
- report digest: `03e1f865714c8bafb72546430781a64a`.

Apply and a no-op rerun retained one run, one evidence row, and two mappings. Both foreign keys were
validated. Rollback restored exactly `Idea` and `P2` with null UUIDs; a second rollback updated zero
rows. Reapply returned to the same category/severity UUID pair.

Transactional negative checks proved that the database rejects:

- copied legacy strings;
- an unknown category UUID;
- a missing severity UUID;
- an inactive category;
- deactivation of the active category default;
- hard deletion of a severity;
- a run whose source count exceeds the configured threshold;
- an unresolved `unknown-category` source value.

The threshold and unresolved-value failures rolled back their run-state changes and left the
source rows untouched. After removing only the disposable fixtures, the database had zero feedback
rows, zero invalid rows, two active definitions, four active categories, four active severities,
and exactly two active defaults. The exact rebuilt candidate then passed startup validation,
returned `{"db":"ok","status":"ok"}`, served both Spanish and English catalog batches with
`ETag: "catalog-2"`, and returned 304 for the matching conditional request.

Focused code verification passed the Haskell executable build, 24 feedback examples, six focused
web tests, 10 focused mobile administration/API tests, web/mobile typechecks, directed lint,
OpenAPI generation, and byte-identical generated clients. These are slice-level results; the
repository-wide suites must be rerun before release.

## Production sequence and rollback boundary

1. Record the exact release SHA, deployed revisions, and a recoverable backup identifier for
   `feedback`, both specialized tables, scoped defaults, catalog runs, and mappings.
2. Deploy the additive schema/catalog bootstrap without enabling the new writer; run the current
   production dry-run and manually resolve any withheld severity.
3. Quiesce legacy feedback writers. Released clients that send copied strings are incompatible and
   must be upgraded or blocked by the coordinated client-version gate.
4. Apply with the exact candidate revision and a reviewed threshold; verify counts, mappings,
   constraints, defaults, and startup checks.
5. Deploy backend and web from the same candidate, verify anonymous submission plus notification
   labels, and monitor invalid-ID responses and catalog latency.
6. If rollback is required, restore the compatible application first and run the guarded rollback
   while writers remain quiesced. Do not delete catalogs, aliases, audit history, mappings, or
   source evidence.

No production backup, migration, deployment, feedback submission, or external publication was
performed during this rehearsal.
