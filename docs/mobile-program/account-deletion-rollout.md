# Account-deletion rollout

`VITE_ACCOUNT_DELETION_FORM_ENABLED` controls new authenticated intake. The independent `VITE_ACCOUNT_DELETION_QUEUE_ENABLED` controls the administrator fulfilment queue. Each accepts only the exact value `true`; absence and all other values keep that surface off. Pausing intake must not disable processing of existing requests. This is rollout control, not server authorization. The existing verified privacy contact remains usable while off, with no claim that a request has been received or that no email is needed.

A reviewed source merge and automatic Cloudflare deployment alone therefore do not qualify this workflow. Keep the production setting absent/false until the canonical backend release includes the strict authenticated owner/session/CSRF boundary and audited administrator resolution, passes its actual HTTP/concurrency tests, and the deployed immutable identity and readiness are verified. Then enable and verify the operator queue first, followed by the intake switch through the existing reviewed deployment procedure. Verify the resulting production build and both user/administrator surfaces. Do not create a real customer deletion request as a smoke fixture. Recovery first disables only the intake switch and rebuilds. Keep the queue enabled and retain a compatible backend while requests remain outstanding. Do not roll back to a backend without the queue/audit endpoints until a verified private operator ledger retains all pending requests, authoritative owners, deadlines and resolution evidence, and operators can continue processing them. A build flag alone cannot qualify that operational handover.

The Playwright webServer explicitly enables both flags only for intercepted synthetic browser fixtures. A separate CI invocation sets `PLAYWRIGHT_ACCOUNT_DELETION_FORM_ENABLED=false`, rebuilds, and verifies the disabled contact path and independently enabled queue on Chromium, Firefox and WebKit. Unit tests cover default-off parsing, both language contact paths, no session/submission requests while intake is off, no queue queries before separate operator enablement, and the existing enabled acceptance and administrator history. Those fixtures are not production availability or a provider/store acceptance result. iOS no-email initiation remains a release prerequisite until the actual enabled backend/web combination is qualified.
