# Account-deletion rollout

`VITE_ACCOUNT_DELETION_FORM_ENABLED` is the public web build switch for the new authenticated request form and administrator fulfilment queue. Only the exact value `true` enables them; absence and every other value keep both off. This is rollout control, not server authorization. The existing verified privacy contact remains usable while off, with no claim that a request has been received or that no email is needed.

A reviewed source merge and automatic Cloudflare deployment alone therefore do not qualify this workflow. Keep the production setting absent/false until the canonical backend release includes the strict authenticated owner/session/CSRF boundary and audited administrator resolution, passes its actual HTTP/concurrency tests, and the deployed immutable identity and readiness are verified. Then enable the web build setting through the existing reviewed deployment procedure and verify the resulting production build and both user/administrator surfaces. Do not create a real customer deletion request as a smoke fixture. An older backend recovery requires disabling this web switch and rebuilding first.

The Playwright webServer explicitly enables the flag only for intercepted synthetic browser fixtures. A separate CI invocation sets `PLAYWRIGHT_ACCOUNT_DELETION_FORM_ENABLED=false`, rebuilds, and verifies the disabled contact path on Chromium, Firefox and WebKit. Unit tests cover default-off parsing, both language contact paths, no session/submission/queue requests while off, and the existing enabled acceptance and administrator history. Those fixtures are not production availability or a provider/store acceptance result. iOS no-email initiation remains a release prerequisite until the actual enabled backend/web combination is qualified.
